## Fix: line breaks typed in admin "Secties" textareas are lost on the storefront

### Root cause
This is a **CSS line-break rendering bug** (not an ordering bug). When the user presses **Shift+Enter** in a "Secties" textarea, the `\n` is stored correctly in the CMS data — I proved the whole pipeline (editor → `patchSectionContent` → `mergeSectionPatch` → zod schema → `normalizeCmsPage` → publish → storefront render) preserves both order and whitespace. The storefront then renders the text in a `<p>` **without** `white-space: pre-line`, so the browser collapses the `\n` into a space per default CSS, and the line break silently disappears.

`privacy.main` / `terms.main` already use `whitespace-pre-line`, which is why those look right and confirms the fix pattern.

### Scope (per your answer: top-level page sections edited in "Secties")
The fixed-section body/intro text fields. I will NOT touch headings, eyebrows, CTAs, or block-internal item fields (those are out of scope for "the following issue only").

### Why `whitespace-pre-line` (not `pre-wrap`)
`pre-line` collapses runs of spaces/tabs but preserves `\n` as line breaks and wraps long lines — exactly textarea behavior. `pre-wrap` would also preserve leading spaces and prevent wrapping of very long lines. `pre-line` matches the existing correct sites (`LegalSections.tsx`) and the textarea's visual model.
